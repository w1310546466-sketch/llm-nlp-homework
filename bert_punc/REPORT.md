# 古文断句：跑完之后和我预想的不太一样

## 先把环境说清楚

之前写方案的时候说"本机没有 GPU"，这个判断是错的。机器上有一张 RTX 4060（8 GB），CUDA 12.5 都装好了，只是 Python 里没有 torch。后来把环境补齐了：torch 2.6.0 + cu124、transformers 4.46.3、bert-base-chinese 权重，都从镜像直接拉的。装的时候遇到一个怪事——pip 一碰网络就挂，报 SSL 握手被重置，`requests` 也是同样的错，但 Python 标准库的 urllib 完全正常。所以最后是用 urllib 把 24 个 wheel 先下下来，再让 pip 只做本地安装。这件事本身没什么技术含量，但耗掉的时间比训练还多。

## 数据怎么做的

人民日报 1998，取两百万字里长度 10 到 120 的句子，切出四万句训练、四千句验证。做法是逐字多分类：把句子里的标点全部删掉作为输入，每个字一个标签，取值是 `O / ，/ 。/ ？/ ！`，标点记在它前面那个字上。

中文 BERT 基本一字一 token，所以字符位置和 token 位置一一对应，不用做子词对齐。这是它比英文省事的地方。如果真的换成会切子词的 tokenizer，就得只保留每个词第一个子词的标签，其余置 -100，否则一个字会重复计分。

## 训练

40k 句、2 轮、batch 32、lr 5e-5，890 秒跑完，显存峰值 6 GB 左右。

第一轮 F1 是 0.9107，第二轮 0.9143。第二轮精确率降了、召回升了，说明模型在往"多标"的方向偏，这是交叉熵在标点稀疏时的常见走向。总的看两轮就到顶了，再加轮数意义不大。

评价这里我特意没报逐字准确率。`O` 占九成以上，全判 `O` 也能有九成多的"准确率"，但模型什么都没学会。只算标点位置的 P/R/F1 才有意义。

## 迁到古文，掉得很厉害

拿《三国演义》开头一千五百字试，F1 只有 0.5013。二十万字版本更低，0.4284。

原因不难理解：模型学的是现代新闻的停顿习惯，不是句法。新闻里"据新华社报道，"这种节奏和"滾滾長江東逝水"完全两回事。看输出会更清楚，它把：

> 滾滾長江東逝水，浪花淘盡英雄。

断成了：

> 滾滾長江東逝，水浪花淘盡，英雄

词界一个没错，停顿全错。它学会了"看到这里大概该喘口气"，但没学会这段韵文的节拍。这个结果比我预期的差，写之前我以为迁到古文至少能到 0.6。

另一个发现是窗口大小不能乱改。训练时 `max_len=128`，推理时如果硬上 510 的窗口，F1 从 0.5013 掉到 0.4444——模型没见过长序列的位置组合，长窗口反而更差。所以"窗口开到最大"不是免费的。

## 批处理到底快了多少

这是这次最出乎意料的部分。

我原来的方案是一万来字，串行做法要三十多次前向，批处理一次就够，差了三十倍。真跑之后发现**那个对比是错的**，因为我拿 128 的窗口去比课件 400 的块，总的 token 量根本没省。

两万字实测：

| 方案 | forward 次数 | 耗时 |
|---|---|---|
| 窗口 128，batch=1 | 270 | 1.872s |
| 窗口 128，batch=32 | 9 | 0.906s |
| 窗口 510，batch=32 | 2 | 0.562s |
| 课件串行（400 取 300） | 58 | 0.747s |

批处理把前向次数从 270 压到 9，但墙钟时间只快一倍左右。课件那种串行做法反而比我 128 窗口的批处理快（0.747 对 0.906），因为它每次吃 400 个 token，总 token 量更少。

那批处理的意义在哪？我认为有两条，但都比原来的说法更弱：

一是**它去掉了对模型输出的依赖**。原来"在句号处决定下一起点"这个设计让每步都得等上一步，这才是串行的根源；改成固定窗口后，窗口可以在跑之前就算好，这是结构性的差别，不是调参能得到的。

二是**在 batch=1 明显跑不满的时候收益才大**。这张卡上 bert-base 跑 128 的长度，batch=32 也只能吃满 6 GB 里的 2 GB 左右，GPU 利用率上不去；如果是 CPU 部署，270 次前向和 9 次前向就是几分钟和几秒的差别。

所以准确的结论是：批处理减少的是调用次数，不是计算量；它值不值，取决于你的部署里调用开销占多大比重。课件说串行"效率很低"，在 400 字块、batch=1 的设定下确实低，但低在没法并行，不在于它浪费了 25%。

## 重叠区怎么裁决

两个窗口重叠的地方，每个字会有两份预测。规则是"离窗口边缘越远越可信"：位置在窗口中间，模型有完整上下文；贴着边界的预测基本靠不住。

实现上是给每个位置记一个 margin（到左右边界的较小距离），取 margin 最大的那次预测。这样每个字只用一次，输出长度严格等于输入长度。窗口切分、裁决、渲染都拆成了纯函数，写了 11 个测试，不需要 GPU 就能跑。

## 还有一些没做的

训练只用了两百万字里的四万句，语料还有十几倍没用上，加数据应该还能涨一两个点，但收益会递减。

古文这边应该做继续预训练或者领域适配，直接零样本迁移本来就不公平，我只报告了现状。

评测取的是标点位置匹配，没有区分"逗号断错位置"和"把句号标成逗号"这两种错误。要细看的话应该分标点类型统计，代码里已经算了 per-class，只是这次没展开。

代码在仓库里，训练和推理都能一条命令复现，只是语料需要自己准备。
